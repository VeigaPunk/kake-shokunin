## 5. Findings
**M1 (medium, observability of the fixture oracle) — the harness compares finding IDs only, so it cannot see row/file identity drift; expected.json carries no row/file field.** `scripts/citing_set_selftest.py` `run_case()` compares `run.returncode` and `sorted(finding_ids(report))` against `sorted(expected["findings"])`; `finding_ids()` discards each finding's `row` and `file`. Demonstrated: in P2 the gate's findings were rows S003/S004/S005/S006 — a different row set than the fixture's S002..S005 — and the harness still reported `verdict clean, passed true, failed 0`. P3 (file drift) was caught only because the id multiset changed (6 unadj + 2 ledger_pair_not_cited), not because identity was compared. Scope/limit: the gate's identity output is correct (section 2 and P2/P3 show exact, correct rows and files), and the frozen C2 oracle `.ufo/waves/round-27/c2_count.py` compares `(row,file)` sets exactly, so C2's own 16/16 identity claim is unaffected. The exposure is fixture-level: a gate emitting the right *count* of `unadjudicated_citing_pair` for the *wrong* rows/files would still pass fixture 03 and the whole fixture suite. This is a fixture-design gap (expected.json schema has no identity field), not a gate defect; the contract's fixture interface (`expected.json {exit:int,findings:[finding-id,...]}`) does not require one — so it is a gap in the declared oracle's discriminating power, not a violation. Recommended (L1 decision, not applied here): extend expected.json with an optional `pairs` list of {row,file} and have the runner compare it when present, keeping the id multiset as the floor.

**No other findings.** No disagreement between my independent derivation and expected.json on exit, finding-id multiset, row identity, or file identity. No defect in the frozen gate's handling of this fixture's en-dash group, metadata-line range, or ledger adjudication.
