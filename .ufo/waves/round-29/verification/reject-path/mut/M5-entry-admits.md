# Project-site base paths on GitHub Pages

Coverage-map ground: project-site base paths (previously Frontier). This entry
owns publisher-side knowledge of the base path; it owns no live property
measurement and claims nothing about any owned site.

**Claim (falsifiable).** A GitHub Pages *project* site is published under a
base path, so a reference written for the origin root does not stay inside the
site, and each toolchain has its own documented remedy: Liquid URL filters
driven by `baseurl` for Jekyll (S041, S042) and the `base` build option for
Vite (S043).

## What a project-site base path is

- GitHub Pages is “a static site hosting service that takes HTML, CSS, and JavaScript files straight from a repository on GitHub” (S040), and “There are two types of GitHub Pages sites. Sites associated with a user or organization account, and sites for a specific project.” (S040).
- The two types differ in published location, not only in repository layout: a project site's default site location is “http(s):/ / <owner>.github.io/ <repositoryname>” (S040, *Default site location* row; the retained text collapses that cell's spacing), while a user or organization site is the host alone (S040, same row).
- S041 agrees from the Jekyll side: project page output “will become available under a subpath of your user pages subdomain, such as username.github.io/project (unless a custom domain is specified)” (S041), and “The subdirectory-like URL structure GitHub uses for Project Pages complicates the proper resolution of URLs.” (S041)

## Which references break

- Root-relative references: under ordinary URL resolution `/style.css` resolves against the origin, not the base path, so on a project site it points outside the site — the condition the Jekyll remedy exists for, “In order to assure your site builds properly, use the handy URL filters” (S041). Policy case `D1-root-relative-stylesheet` in `.ufo/waves/round-29/c2-matrix.json` pins it.
- Escapes above the base path: a relative reference that walks upward (`../other/`) resolves outside the base path on a page served under it (S041, on resolution under a subdirectory-like URL structure). The lane audit policy names this class `outside_base_path`.
- A base element: a `<base href>` changes what every relative reference resolves against, so `<base href="/">` sends relative references to the origin root, out of a project site. Only the first base element with an `href` applies; the lane already holds that rule in `corpus/knowledge/static-canonical-preflight.md`, and matrix cases `D7` and `K6` pin it for the audit. None of S040–S043 discusses the base element.

## The Jekyll remedy

- Pages generates the site at publish time — “Your site is automatically generated by GitHub Pages when you push your source files.” (S041) — and Pages “optionally runs the files through a build process” (S040); with Jekyll that build is where the base path enters.
- Use the URL filters rather than hard-coded paths: `relative_url` for assets with static names, `absolute_url` for page URLs that can change (S041).
- `relative_url` “Prepend baseurl config value to the input to convert a URL path into a relative URL. This is recommended for a site that is hosted on a subpath of a domain.” (S042), worked example “{{ "/assets/style.css" | relative_url }} /my-baseurl/assets/style.css” (S042).
- `absolute_url` “Prepend url and baseurl values to the input to convert a URL path to an absolute URL.” (S042), worked example “{{ "/assets/style.css" | absolute_url }} http://example.com/my-baseurl/assets/style.css” (S042).
- The `baseurl` value must match the published base path, so a local preview empties it: “bundle exec jekyll serve --baseurl = ""” (S041); with the filters “This way you can preview your site locally from the site root on localhost, but when GitHub generates your pages from the gh-pages branch all the URLs will resolve properly.” (S041)

## The Vite remedy

- Vite bakes the base into the build output, so set it before the build: “Set the correct base in vite.config.js .” (S043).
- Project site: “If you are deploying to https://<USERNAME>.github.io/<REPO>/ (eg. your repository is at https://github.com/<USERNAME>/<REPO> ), then set base to '/<REPO>/' .” (S043).
- User site or custom domain: “If you are deploying to https://<USERNAME>.github.io/ , or to a custom domain through GitHub Pages (eg. www.example.com ), set base to '/' .” (S043); “Alternatively, you can remove base from the configuration, as it defaults to '/' .” (S043).
- Pages does not run Vite: “GitHub will now deploy your site using a GitHub Actions workflow , which is necessary since Vite requires a build step for deployment.” (S043).

## What changes under a custom domain

- “You can host your site on GitHub's github.io domain or your own custom domain.” (S040).
- The repository name does not change with the domain: “Custom domains do not affect repository names” (S041); a user or organization site is still “initially configured to live under the username.github.io subdomain” (S041).
- A project site under a custom domain is published at the domain root instead of the repository-name subpath — S041’s “(unless a custom domain is specified)” (S041) and S043’s `base` of `'/'` for a custom domain (S043). S040 itself states only that a custom domain is possible.
- [INFERENCE] One artifact serves one shape: a build with `base`/`baseurl` of `/<REPO>/` carries prefixed URLs and does not fit a domain-root publication, and a build for the domain root carries root-relative URLs that leave a project site. Moving between the two shapes needs a rebuild, not a redirect.

## What the lane can and cannot check offline

- Can: `scripts/base_path_audit.py` reads a local manifest `{version, basePath, pages:[{file, url}]}` and resolves each local page's reference set (`a`/`area`/`link` `href`; `img`/`script`/`iframe`/`source`/`audio`/`video`/`track`/`embed` `src`; `img`/`source` `srcset`; `video` `poster`; `form` `action`) against `basePath`, honouring the first base element with an `href`; finding reasons are `outside_base_path`, `input_invalid`, `page_outside_base_path`.
- Can: the frozen 30-case matrix is `.ufo/waves/round-29/c2-matrix.json`; the counter is `python3 -B .ufo/waves/round-29/c2_matrix_count.py --root . --revision <commit>`.
- Cannot: the audit reads local files only. It cannot show what a server returns, confirm the base path a deployed site is served under, verify a custom-domain mapping, tell whether an out-of-base reference is missing or merely redirected, or identify which repository publishes a site. A clean audit says only that the audited files match the declared base path.
- Not established here: the base path, domain or build mode of any owned property; that needs an authorized read of the published property or of the Pages configuration.
