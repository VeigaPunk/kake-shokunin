# SentinelToolInputs — wave-2 falsify report (r35, C1)
Attacks the round-35 C1 repair `scripts/link_preview_audit.py` at `b1cbbc39` (sha256 `1a8b2724…f5ef4`) with hostile page inputs. **Finding 1 (High): the new suppression stack makes parsing quadratic — a page the pre-repair tool parsed in 0.24 s now runs 499 s and is killed by `timeout 60` with no JSON.** Sandbox `/fast/scratch/hyaku/kake-r35/w2/SentinelToolInputs/` (clone at `b1cbbc39`, base at `16a6b8b8`); no lane file modified.
## Finding 1 (High) — quadratic end-tag scan: 499 s / timeout, no JSON output
Mechanism: `scripts/link_preview_audit.py:106-112` (new in `b1cbbc39`; base has no `handle_endtag`) walks the whole `suppressed_elements` list backwards on **every** end tag, and `handle_starttag:98-104` pushes one entry per suppressed start tag and never pops on a non-matching end tag. N suppressed opens then M non-matching end tags cost O(N·M) — both are attacker-chosen bytes of the page. Exploit path: any local page named by a manifest — `"<template>"*100000` then `"</svg>"*100000` — stalls the audit gate, and since the tool prints nothing until it finishes, the caller gets no verdict. The shipped selftest timeout is 120 s (`link_preview_selftest.py:15`), so a hostile fixture trips that too.
Evidence (sandbox commands; exit codes as shown):
1. `timeout 60 python3 -B run_one.py C2_nested_open_unmatched_ends` → exit 124, `timed_out: true`, `wall_s 60.064`, **`json_valid: false`**, `stdout_len 0`. Same manifest on the base tool: exit 1, 0.244 s, valid JSON.
2. `timeout 900 python3 -B c2_long.py new <C2 manifest> 600` → `exit 1 wall 499.191 rss_kb 26012 json_ok True` — it finishes, after **499 s** for a 1.6 MB page.
3. `python3 -B scale.py` (page = `"<template>"*n + "</svg>"*n`): n=2000 0.117 s, 4000 0.359 s, 8000 1.329 s, 16000 5.341 s, 32000 21.233 s → ratios 3.07/3.70/4.02/3.98, ~4x per doubling = quadratic. Base on the n=32000 page: 0.244 s.
4. `python3 -B model.py` (fixed 50000 end tags, growing depth): 1000→1.006 s, 2000→1.911 s, 4000→4.919 s, 8000→9.703 s, 16000→20.873 s (linear in depth); base on depth 16000: 0.151 s.
5. `python3 -B micro.py` (real `MetadataParser` vs the same parser with a no-op `handle_endtag`): 5000/5000 0.938 vs 0.028 s; 10000 3.743 vs 0.044 s; 20000 19.884 vs 0.244 s; 40000 92.314 vs 0.464 s — the gap is entirely `handle_endtag`.
6. `python3 -B practical.py` (unclosed `<svg>` opens then ordinary `</p>` closes): 500+1000 → 0.145 s (base 0.092); 2000+20000 → 1.435 s (base 0.264); 5000+20000 → 3.790 s (base 0.148, **25.6x**).
7. `python3 -B run_big.py` on a 13.5 MB page (`"<template>"*1000000 + "</svg>"*590000`) → `exit None wall 180.113 json_ok False rss_kb 100100`: killed at 180 s with no report.
8. `python3 -B rss2.py new|base` on a 16 MiB page of 3.35 M `<svg>` opens: new rss 238 580 kB vs base 49 848 kB (**4.8x**); `python3 -B memscale` shows RSS tracks open count, not page bytes (100 k opens 24 MB, 400 k 44 MB, 1.6 M 124 MB).
Impact: the 16 MiB page bound does not bound the work — 1.6 MB costs 499 s. Smallest remediation: guard the scan with a per-name open count so a non-matching end tag is O(1). Verified in the sandbox only (`python3 -B remedy.py`; patched copy `…/SentinelToolInputs/patched_link_preview_audit.py`, lane file untouched): **0 mismatches across all 46 committed selftest fixtures** (identical exit and stdout for each) and hostile inputs drop to 100k+100k `TIMEOUT/90.105 s` → `exit 1 / 0.665 s`; 50k svg + 50k `</template>` 61.999 s → 0.146 s; 20k+20k 28.833 s → 0.078 s. Alternatively bound the suppression stack depth and report `page_unreadable` past a small constant.
## Finding 2 (Medium, UNCONFIRMED) — the 16 MiB read bound is a stat-before-read check
`scripts/link_preview_audit.py:228-230` checks `file_path.stat().st_size > MAX_PAGE_BYTES` then calls `file_path.read_text()`, which has no size cap of its own. I tried to land a growing file inside the stat→read window (`readbound2.py`, `sweep2.py` over delays 0.005–0.080 s, plus `grow.py`, `grow2.py`, `growcount.py`, `unbounded.py`, `unbounded2.py`, `toctou*.py`, `fdbound.py`): **the bound was never bypassed.** Every run was either caught by the stat (`page_unreadable`, exit 2) or read exactly the on-disk size; the stat→read gap is sub-millisecond and I could not time into it. The code shape leaves the read unbounded, so a bounded read (`read(MAX_PAGE_BYTES+1)`, reject on overflow) is worth considering as defence in depth — but I claim no demonstrated defect here.
