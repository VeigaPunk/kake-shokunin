# SentinelSandbox — Round 41

Axis: operability. Read-only source review plus harmless local sandbox probes; no lane code edited. Runtime: bubblewrap 0.13.1, Python 3.14.8.

## Findings

- **HIGH — launcher environment readable by the untrusted tool** (`.ufo/waves/round-41/c1_count.py:245,247,346-347`). `--proc /proc` exposes PID 1, which is `bwrap` and retains the caller's environment: `subprocess.run` passes the parent environment by default, while `--clearenv` clears only the executed tool's environment. A redacted canary probe saw tool env keys `LANG, PATH, PWD`, but read 263 keys from `/proc/1/environ`, including a synthetic canary. The canary probe retained no values beyond its synthetic value. An earlier FD diagnostic emitted raw `/proc/1/environ` into a captured tool-output artifact; I did not inspect that full artifact, so its contents are unreviewed and are not reproduced here. **Exploit path:** arbitrary tool reads `/proc/1/environ`; any credentials present in the runner environment are exposed to it. Its output can influence the captured score/receipt. Actual secret presence is unverified; no oracle label was observed. **Impact:** conditional disclosure of runner environment secrets. **Smallest remediation:** pass a sanitized `env=` allowlist to the bwrap `subprocess.run` itself (and retain only required variables).
- **MEDIUM — scorer stdin is inherited** (`c1_count.py:346-347`). No `stdin=` is supplied. A harmless probe received a synthetic piped sentinel through the sandbox. **Impact:** a tool can read any data supplied to the counter's stdin. **Smallest remediation:** `stdin=subprocess.DEVNULL`.
- **LOW — host metadata and mount source paths are visible** (`c1_count.py:245-249`). `/proc/1/cmdline` exposed bwrap's source arguments; `/proc/self/mountinfo` exposed bind-source roots/device metadata. `/proc` also exposed host nodename, kernel release, uptime and load. These observations did not expose the counter's `--label`, seed, oracle booleans or parent process; no direct correlation with expected labels was seen. **Impact:** runner layout/system metadata disclosure; paths are not readable merely because they appear in proc. **Smallest remediation:** document this visibility, or hide/filter proc metadata if pathname confidentiality is required.
- **MEDIUM — output capture has no byte cap** (`c1_count.py:346-349`, `:42`). `capture_output=True` buffers arbitrary stdout and stderr; stdout is later decoded and parsed. The 600-second timeout limits duration, not output volume; the external 4-GB address-space cap is not enforced by the counter itself. **Impact:** a malicious tool can exhaust the scorer's memory. **Smallest remediation:** enforce bounded output while reading and fail once the limit is exceeded.

**Filesystem/process result:** `/usr`, the case directory and tool were read-only in mountinfo. `/tmp` and the sandbox root were private writable tmpfs; `/proc` and `/dev` were namespace mounts. I found no shared filesystem write path the counter later reads; stdout/stderr are intentional captured channels (stderr is ignored; stdout is judged). `/proc` showed only sandbox PIDs 1 (`bwrap`) and 2 (tool). A 2-second timeout probe killed its sleeping descendant: no descendant PID remained.

- Oracle labels stay out of the tool input: **holds as direct data flow**; only values/manifest/sitemap records are mounted (`:188-239`). Their correctness is, necessarily, inferable by judging those values. No direct oracle-bit leak was found.
- No selftest half: **holds** in the inspected `main` (`:275-369`).
