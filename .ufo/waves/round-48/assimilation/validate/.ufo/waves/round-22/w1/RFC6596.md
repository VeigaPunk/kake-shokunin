# RFC 6596 — Section 3: canonical relation semantics and relative IRI

**Source.** https://www.rfc-editor.org/rfc/rfc6596.html — *The Canonical Link Relation* (M. Ohye, J. Kupke), April 2012, Informational.
**Accessed.** 2026-10-20 (UTC, ~21:33Z).
**Section.** §3 "The Canonical Link Relation" (quotes at §3, p. 2).
**Errata.** none found (errata.rfc-editor.org search for RFC 6596, same access date).

## Exact located quotes (verbatim, line-wrapped text rejoined)

Relative IRI, §3, first bullet under "The target (canonical) IRI MAY:" (8 words):

> "Specify a relative IRI (see [RFC3986], Section 4.2)."

Semantics, §3 opening sentence (22 words):

> "The target (canonical) IRI MUST identify content that is either duplicative or a superset of the content at the context (referring) IRI."

## Observed facts (paraphrase, same section)

- Target MAY be self-referential (context IRI identical to target IRI).
- Target MAY exist on a different hostname or domain, and MAY have a different scheme (example: "http" to "https", "gopher" to "ftp").
- Target MAY be a superset of context content; a component page SHOULD NOT canonicalize to a sibling component page (data-loss argument), e.g. page-2.html SHOULD NOT designate page-1.html.
- Administrators "ought to" specify only one canonical link relation per resource; avoid designating as target a permanent-redirect source (HTTP 300/301), an IRI that itself canonicalizes elsewhere, an IRI returning 4xx, or the first page of a multi-page article.
- Improper declarations (chained canonicals, 4xx target) may be handled by application heuristics; applications may ignore an improper designation.
- IANA registered the `canonical` relation per RFC 5988.

## Scoped teaches for the C1 preflight

1. **Relative IRI is permitted, not an error.** `relative_same_dir`, `relative_parent`, `root_relative` and `scheme_relative` inputs are valid canonical declarations when they resolve to the manifest's `expectedCanonical`. RFC 6596 only grants the permission; the resolution algorithm is RFC 3986 §4.2/§5, which the validator must implement (scheme-relative is RFC 3986 syntax, an RFC 3986 dependency rather than an RFC 6596 allowance explicitly enumerated).
2. **Self-reference is permitted.** `absolute_match` is the healthy positive control, not a degenerate case.
3. **Cross-host / cross-scheme mismatch is local policy, not an RFC violation.** Matrix cases `wrong_host`, `wrong_path`, `wrong_query` (and scheme changes) fail only because they diverge from the manifest's expected IRI. RFC 6596 explicitly permits a different host/domain and scheme; the finding text must not claim RFC non-conformance.
4. **Duplicate links: reject on guidance, mark the basis.** "Specify only one canonical link relation" is administrator guidance ("ought to"), so `duplicate_same` / `duplicate_different` rejection is C1 policy informed by §3, not an RFC MUST. Finding ids should stay policy-scoped.
5. **Semantics cannot be verified statically.** The single MUST is content-level (duplicative or superset). An offline validator can only compare declared IRIs; it cannot prove duplicate/superset content. Do not encode a "content-superset verified" claim in output.
6. **Out of scope by source, not by omission of the validator:** HTML parsing (`first_base`/`second_base_ignored`, `attr_uppercase`, `rel_token_list`, `rel_uppercase`, `entity_href`, `comment_decoy`, `script_decoy`, `template_decoy`, `body_link`, `missing_head`) and IRI syntax/equality (`invalid_url`, `javascript_url`, `data_url`, `fragment_url`, percent/case normalization) are defined by the HTML Standard, RFC 3986 §6, and local policy respectively. RFC 6596 does not adjudicate them.

## Limitations of this source

- **Informational, not Standards Track.** One RFC 2119 MUST; everything about uniqueness, redirects, 4xx, first-page avoidance, and cross-host targeting is guidance or "MAY"/heuristic language. It cannot by itself justify hard-fail conformance language.
- **No resolution, comparison, or normalization rules.** Relative-IRI mechanics and equivalence are delegated to RFC 3986; RFC 6596 says nothing about default ports, case, or percent-encoding.
- **No HTML mechanics, no HTTP header requirement, no redirect/status checking.** HTTP `Link` header (`rel="canonical"`) is RFC 5988 territory (now RFC 8288); redirect/status references cite the obsolete RFC 2616 (superseded by RFC 7231/9110).
- **No error reporting model.** Exit codes, finding ids, and JSON schema come from the frozen contract, not this RFC.
- **Silent on fragment-only and non-HTTP(S) schemes.** The matrix expectations for `fragment_url`, `javascript_url`, `data_url` need a different authority or explicit local-policy citation; RFC 6596 neither permits nor forbids them by name.

## Source status recommendation

Cite as **RFC 6596 (Informational, April 2012), no errata at access**. Use as the primary, non-normative source for: canonical relation meaning (preferred IRI over duplicative/superset content), permission for relative/self-referential/cross-host/cross-scheme targets, and the single-canonical guidance. Do **not** cite it as the conformance authority for URL resolution, HTML head/base parsing, HTTP `Link` headers, redirect/4xx checks, or IRI equality; those need RFC 3986 / HTML Standard / RFC 8288 respectively. Recommended corpus tag: informational upstream semantics, C1 policy layer local.

## Remaining unknowns

None material for the scoped question. One boundary to keep explicit downstream: RFC 6596's cross-host allowance and the matrix's `wrong_host` expectation are reconciled only by `expectedCanonical` being the policy oracle; if a later manifest omits expected IRIs, RFC 6596 alone cannot reject a cross-host canonical.
