## Findings

1. **`publisherCheck` narrows the shortcut condition to one key.** Exact substring: `"whether it fires on a single letter (any case), punctuation, number, or symbol key with no modifier key such as Ctrl or Alt."` The criterion at `#character-key-shortcuts` applies when a shortcut is implemented using *only* the listed character types; it does not say it must be a single character. The linked shortcut definition at `#dfn-keyboard-shortcuts` expressly permits one or more keys. As written, the check can miss multi-key combinations or sequences made only of those characters. **Minimal correction:** replace `on a single ... key` with wording that checks shortcuts composed only of the listed character keys, including multi-key combinations/sequences, and distinguishes those from shortcuts containing a non-printable key.

2. **`evidenceNeeded` overstates the focus alternative as global key inertness.** Exact substring: `"a human observation that the key does nothing while focus is elsewhere, including while typing in a text field."` At `#character-key-shortcuts`, the requirement is that *the shortcut for that user interface component* is active only when that component has focus—not that the character key has no effect or that no other component may respond. The definition/notes at `#dfn-user-interface-components` specifically include form elements and treat separately perceived controls as components, so ordinary text entry or a different focused control can still use the same character. **Minimal correction:** require observing that this component's shortcut does not activate while its component lacks focus (and, for completeness, that it activates when that component is focused); do not require the key itself to have no effect elsewhere.
