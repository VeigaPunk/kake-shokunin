## 2. Findings (severity order; every expectation declared before the run)
**F1 [HIGH] Silent green when population ids cannot be produced by the citation grammar.** `load_population` accepts any non-blank string id, but `scan_text` emits only `S`+≥3 digits (`(?<!\w)S([0-9]{3,})(?!\w)`); ranges expand only to `("n", int)`. Other ids are unreachable. Declared: an unsupported population must not yield clean/green. Observed P22 (population `{"rows":[{"id":"S01"},{"id":"S02"}]}`, corpus `See S01 and S02 for details.`, ledger `{"pairs":[]}`): `exit 0`, `{"verdict":"clean","citingPairs":0,"ledgerPairs":0,"findings":[],"populationRows":2,"corpusFiles":1,"outsidePopulation":0}`. Same for non-numeric `A01/B02` (P22b). The gate is then structurally incapable of its red finding; `populationRows 2 / citingPairs 0` is the only trace. The docstring claims non-`S` ids are "compared as an exact string" — support the scanner cannot deliver. Whitespace ids die the same way: `" S001 "` → `populationRows 4` but `citingPairs 2`, `S001` falls into `outsidePopulation` (P40).
**F2 [HIGH] Green when `corpus/knowledge` is absent or empty.** `WorkingTreeSource.corpus_files()` returns `[]` on `FileNotFoundError`; `GitSource.corpus_files()` returns `[]` when the pathspec matches nothing. Declared: absent/unreadable corpus must not be green. Observed P21b (corpus dir removed, empty ledger): `exit 0`, `{"verdict":"clean",...,"populationRows":4,"corpusFiles":0,"findings":[]}`. Same tree with a populated ledger fails safe (`exit 1`, 4×`ledger_pair_not_cited`, P21); git mode behaves identically (P32). No floor on `corpusFiles`, so a green with zero obligations is reachable whenever the ledger is empty; a wrong `--root`/`--revision` yields it silently.
**F3 [MEDIUM] Deeply nested JSON crashes the gate: exit 1, no JSON on stdout.** `load_json_document` catches `ValueError`; deep nesting raises `RecursionError` (not a `ValueError`). Declared: unusable input ⇒ exit 2 **and** a JSON report (contract: "The JSON document is written to stdout in every mode"). Observed depths 200000/400000 (P46): `exit 1`, stdout **not** JSON, stderr `RecursionError: Stack overflow (used 8144 kB) while decoding a JSON array from a unicode string`. Depths 60000/100000/150000 crash; 50000 parses → `exit 2`/`document_shape_invalid` — the threshold is stack-dependent, so the same input may pass or crash by machine. Exit 1 is the contract's "failed (findings present)": a malformed input is reported as a red *finding* failure with no machine-readable output.
**F4 [MEDIUM] `--revision ""` silently switches the gate to working-tree mode.** `main()` uses `if arguments.revision:`; the empty string is falsy. Declared: an empty revision must not silently change the measurement basis. Observed P47: `exit 1`, report `"source":"working-tree"`, `"revision":null` — blob mode requested, working tree measured, no diagnostic.
**F5 [LOW-MED] Git-blob mode drops the failing document and mislabels the scope.** `GitSource._git` raises `InputInvalid("git_command_failed", None, "revision", command=…)`: no `path`, scope `revision` although the revision resolved. Declared: git mode must identify *which* document failed, as working-tree mode does. Observed P30 (git, population absent at the revision): `{"id":"input_invalid","reason":"git_command_failed","scope":"revision","command":"show <sha>:population.json"}` — the path survives only inside the `command` string and git's message is dropped. Working-tree counterpart P30b: `{"reason":"document_unreadable","scope":"document","path":"population.json","detail":"No such file or directory"}`. A consumer keying on `path` sees nothing in git mode.
**F6 [LOW-MED] Docstring claim "its endpoints remain literal citations" is false for glued alphabetic separators.** The token regex needs a non-word char after the digits; in `S006toS001` the `t` is a word char. Declared: endpoints still cited. Observed P35: `exit 1`, `{"id":"citation_range_invalid"}`, `citingPairs 0` — neither endpoint counted. Spaced `S006 - S001` (P35b) gives `citingPairs 2` (`-` is not a word char). A pair cited only inside a descending glued range is invisible to the citing set, so it is never demanded of the ledger.
**F7 [LOW] Range-span limit off by one against the prose.** Code rejects `end-start > 200` (≥202 ids); the docstring rejects "spans more than 200 ids" (201 ids). Observed: `S001-S201` → accepted, 201 `unadjudicated_citing_pair`, no `citation_range_invalid` (P33); `S001-S202` → `citation_range_invalid` (P34). The contract's ">200 span" is ambiguous (end−start vs id count) and needs a declared tie-break; code and prose differ by one.
**F8 [LOW, robustness] Duplicate / nonfinite members accepted silently.** Duplicate JSON object members `{"rows":[{"id":"S001"}],"rows":[{"id":"S002"}]}` → last-wins, `populationRows 1`, no signal (P24). `NaN`/`Infinity` as members → accepted (Python `json` allows them; `parse_constant` not overridden), no `input_invalid` (P25); as a row *id* correctly rejected (P25b, exit 2). Duplicate population rows → `populationRows 5` for 4 ids, no finding, while duplicate *ledger* pairs raise `ledger_duplicate_pair` (fixture 11) — asymmetric (P23). `"S001"`+`"S0001"` are one id under the gate's own numeric comparison; the alias is invisible (P36). Contract/QUALITY make neither duplicates nor non-finites invalid ⇒ robustness findings, not contract violations.
**F9 [LOW] Loader/comparator normalisation is inconsistent.** `load_ledger` trims `file` but not `row`; `load_population` tests `identifier.strip()` but stores the untrimmed id; `normalize_ledger_file` strips `./` but not `..`. Declared: a stray space must not desynchronise the ledger from the citing set. Observed P41 (ledger row `"S001 "`): the same pair is reported **both** `ledger_pair_not_cited` and `unadjudicated_citing_pair` (`citingPairs 3`); same contradiction for a `..` ledger path (P42). Fails safe (red) but yields two contradictory findings for one pair.
**F10 [LOW] Mode asymmetry on an odd corpus shape.** Declared: same tree ⇒ same verdict in both modes. Observed: `corpus/knowledge` as a regular file → working-tree `exit 2` `not_a_directory` (P60); the same committed tree in git mode → `exit 1`, the blob scanned as a document named `corpus/knowledge` (P60b). `GitSource.corpus_files()` accepts the pathspec blob itself.
**F11 [LOW, observational] Unreadable corpus file still emits `ledger_pair_not_cited` for its pairs.** P20 (chmod 000) → `exit 2`, findings = `input_invalid` + 4×`ledger_pair_not_cited`; P27 (non-UTF-8) same shape. Verdict/exit correct (2, `could-not-evaluate`) ⇒ no false green, but a consumer counting findings by id — as the fixture runner does — sees obligations that are artefacts of the unreadable file.
**F12 [MEDIUM, operability] The shipped selftest does not cover the attacked boundaries.** `scripts/citing_set_selftest.py:run_case` builds `argv` without `--revision` ⇒ the Git-blob reader has **zero** fixture coverage; `c2_count.py` also runs the gate working-tree-only, so no shipped consumer exercises `GitSource` — the mode where F5/F10 live is operator-only. The 29 shipped fixtures cover invalid-JSON **population** (15) and invalid population shape (16) only; no invalid-JSON ledger, no invalid ledger shape, no missing-document, no unreadable-corpus, no empty-corpus, no non-finite/duplicate fixture. Observed: `citing_set.py --selftest --root .` → `exit 0`, `verdict clean`, `cases 29, failed 0` — the gap is invisible to the shipped check.
