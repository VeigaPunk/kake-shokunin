**F1 — LOW (robustness, not a false green): non-UTF-8 filename makes revision mode unevaluable for the whole run.**
- Line: 88 (`_nul_paths`: `chunk.decode("utf-8", "replace")`), consumed at 182-183, failure surfaces at 187 (`return None, f"cannot read {rel} at {revision[:12]}"`).
- Input: a knowledge file whose name is not valid UTF-8, e.g. `corpus/knowledge/bad\xff.md` committed to a fixture repo, then `--revision <that commit>`. `git ls-tree -r -z` emits the raw bytes; `decode(..., "replace")` turns `\xff` into U+FFFD, the subsequent `git show <rev>:corpus/knowledge/bad\ufffd.md` cannot match the tree entry, and `knowledge_bodies` aborts: observed `status=2 error='cannot read corpus/knowledge/bad\ufffd.md at 0bdd7173e007'`. One exotic filename therefore denies the entire revision-mode evaluation (exit 2 "unevaluable"), instead of reading the other files.
- Fix: `chunk.decode("utf-8", "surrogateescape")` (equivalently `os.fsdecode(chunk)`): subprocess encodes `str` argv with surrogateescape, so `git show <rev>:<path>` round-trips the original bytes. Caveat to note in the fix: rendering such a path in a `DANGLING cited-by=` line can raise UnicodeEncodeError under a strict-UTF-8 stdout; if that is unacceptable, decode with surrogateescape only for the `git show` argument and keep a replacement-decoded copy for display.
- Not silent: the failure is loud (exit 2), so it cannot fake a clean C2 run. Severity Low.
