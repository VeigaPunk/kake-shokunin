FINDINGS:

1. LOW — K4/K5 red control is host-gitconfig sensitive. Base tool filters `git ls-tree -r --name-only` names by `startswith("corpus/knowledge/")`/`endswith(".md")` (id_resolver.py:144-150); with `core.quotePath` at its default true, `中文.md`/`a"b.md` arrive quoted and are dropped (K4/K5 red, confirmed by running: base 7/12, K4/K5 `exit=0 ids_cited=1`). A host with global `core.quotePath=false` would show base 9/12. The counter cannot pin this: its `env()` strips inherited `GIT_*`, and the tool's `_spawn` (id_resolver.py:62-65) would strip any `GIT_CONFIG_GLOBAL` the counter tried to set. Verdict is unaffected (12/12 is unreachable at base either way), but the frozen 7/12 base receipt is only reproducible on default-config hosts. This host is clean (`git config --global --list`: only `init.defaultbranch=main`).
2. LOW — infrastructure failure exits 1, colliding with "not met". `repo()` raises `RuntimeError` on a toplevel mismatch and `run()` can raise `subprocess.TimeoutExpired`; neither is caught in `main()`, so Python exits 1 with a traceback — indistinguishable from a scored "not met" (documented codes 0/1/2/64). Not a false-green vector; it mislabels an infra crash. Suggest wrapping `measure()` and mapping to 2. [INFERENCE on timeout path — not triggered in my runs; crash path unexercised by design.]
3. INFO — P2 pins the line-based registry model and is GFM-divergent. Under CommonMark+GFM reference parsing, `| S002 |…|` after a closed fence (no header/delimiter row, file ends) is a paragraph, not a table row; the counter requires it to resolve. That is exactly the contract docstring's rule ("first cell of each table row (a one-cell row counts)… 0 to 3 leading spaces"), so P2 is contract-correct — but it forbids any fix that re-implements `parse_registry` on a real markdown AST. Consequence for the executor: the fix must stay a line scanner with fence tracking; do not swap in a CommonMark/GFM parser.
4. INFO — P6 floor `>= 49` equals the current selftest size exactly (49 entries in `_cases()`, id_resolver.py:794-846; run shows `49/49`). It is a no-regression pin: any fix that consolidates or drops even one case fails P6. Intentional-looking and disclosed, but tight.
5. INFO — P7 floor `>= 106` equals base `ids_cited` exactly (confirmed by running: `ids_cited=106 ids_resolved=106 dangling=0`). C3 cannot break it: S423/S424 add citations and registry rows together, so ids_cited only rises and dangling stays 0 at any revision containing C3; when the counter runs at the frozen base (the scoring flow), C3 is invisible (blobs read via `git show`, never the worktree). No P7/C3 interaction risk.
6. NIT — cosmetic: P6's note prints the raw tuple (`('49', '49')`); `measure()`'s tool-absent path returns one result row yet `main()` prints `0/12`; `check()` concatenates stderr+stdout before matching, so an unterminated stderr line could fuse into a stdout `^` anchor (never observed — tool diagnostics are newline-terminated); the tool's `--selftest` sandboxes follow `$TMPDIR`, not `--work` (run the counter with `TMPDIR` under the seat scratch; I did).
