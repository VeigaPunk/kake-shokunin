# Project-site base paths on GitHub Pages

Coverage-map ground: project-site base paths (previously Frontier). This entry
owns publisher-side knowledge of the base path; it owns no live property
measurement and claims nothing about any owned site.

**Claim (falsifiable).** A GitHub Pages *project* site is published under a
base path, so a reference written for the origin root does not stay inside the
site, and each toolchain has its own documented remedy: Liquid URL filters
driven by `baseurl` (and `url`, for `absolute_url`) for Jekyll (S041, S042) and the `base` build option for
Vite (S043).

## What a project-site base path is

- GitHub Pages is “a static site hosting service that takes HTML, CSS, and JavaScript files straight from a repository on GitHub” (S040), and “There are two types of GitHub Pages sites. Sites associated with a user or organization account, and sites for a specific project.” (S040).
- The two types differ in default published location, not only in repository layout: a project site's default site location is “http(s):/ / <owner>.github.io/ <repositoryname>” (S040, *Default site location* row; the published cell has no spaces, and the retained plain text inserts one at each line-break tag), while a user or organization site is the host alone (S040, same row).
- S041 agrees from the Jekyll side for branch or `docs`-folder publishing (it says nothing about Actions publishing): project page output “will become available under a subpath of your user pages subdomain, such as username.github.io/project (unless a custom domain is specified)” (S041), and “The subdirectory-like URL structure GitHub uses for Project Pages complicates the proper resolution of URLs.” (S041)

## Which references break

- Root-relative references: [INFERENCE] under ordinary URL resolution `/style.css` resolves against the origin, not the base path, so on a project site it points outside the site; none of S040–S043 states this or says what the server then returns. S041 only says the subdirectory-like structure complicates URL resolution and prescribes the URL filters: “In order to assure your site builds properly, use the handy URL filters” (S041). Policy case `D1-root-relative-stylesheet` in `.ufo/waves/round-29/c2-matrix.json` pins the audit's reading.
- Escapes above the base path: [INFERENCE] a relative reference with more `../` steps than the page's depth below the base path (`../other/` on the base-root page) resolves outside the base path; on a page one level deeper, `../a.css` stays inside. No source id: this is URL resolution, pinned by matrix cases `D4` and `D11`. The lane audit policy names this class `outside_base_path`.
- A base element: [INFERENCE] a `<base href>` changes what every relative reference resolves against, so `<base href="/">` sends relative references to the origin root, out of a project site. Only the first base element with an `href` applies; the lane already holds that rule, with its source, in `corpus/knowledge/static-canonical-preflight.md`, and matrix cases `D7` and `K6` pin it for the audit. None of S040–S043 discusses the base element.

## The Jekyll remedy

- Pages can generate the site at publish time — “Your site is automatically generated by GitHub Pages when you push your source files.” (S041) — and Pages “optionally runs the files through a build process” (S040). [INFERENCE] When Jekyll builds the site, `relative_url` adds `baseurl` during that build (S042); a repository that pushes already generated HTML gets no such step, so its HTML must already carry the base path.
- Use the URL filter rather than hard-coded paths: S041 writes both a static-name stylesheet and `page.url` through `relative_url` (S041). S041 does not mention `absolute_url`; that filter is defined only in S042.
- `relative_url` “Prepend baseurl config value to the input to convert a URL path into a relative URL. This is recommended for a site that is hosted on a subpath of a domain.” (S042), worked example “{{ "/assets/style.css" | relative_url }} /my-baseurl/assets/style.css” (S042).
- `absolute_url` “Prepend url and baseurl values to the input to convert a URL path to an absolute URL.” (S042), worked example “{{ "/assets/style.css" | absolute_url }} http://example.com/my-baseurl/assets/style.css” (S042).
- A local preview from the site root overrides the base path on the command line: S041 shows `bundle exec jekyll serve --baseurl=""` (the retained plain text reads `--baseurl = ""` because tag removal adds spaces; the page HTML has no spaces around `=`), and with the filters “This way you can preview your site locally from the site root on localhost, but when GitHub generates your pages from the gh-pages branch all the URLs will resolve properly.” (S041)

## The Vite remedy

- Set the base in the Vite configuration: “Set the correct base in vite.config.js .” (S043). [INFERENCE] Vite writes the base into the built files, so changing it means rebuilding.
- Project site: “If you are deploying to https://<USERNAME>.github.io/<REPO>/ (eg. your repository is at https://github.com/<USERNAME>/<REPO> ), then set base to '/<REPO>/' .” (S043; the spaces before `)` and `.` come from tag removal in the retained plain text, not from the page).
- User site or custom domain: “If you are deploying to https://<USERNAME>.github.io/ , or to a custom domain through GitHub Pages (eg. www.example.com ), set base to '/' .” (S043); “Alternatively, you can remove base from the configuration, as it defaults to '/' .” (S043).
- A Vite site on Pages is published from a GitHub Actions workflow that runs the build: “GitHub will now deploy your site using a GitHub Actions workflow , which is necessary since Vite requires a build step for deployment.” (S043), after “Under Build and deployment , open the Source dropdown, and select GitHub Actions .” (S043).

## What changes under a custom domain

- “You can host your site on GitHub's github.io domain or your own custom domain.” (S040).
- The repository name does not change with the domain: “Custom domains do not affect repository names” (S041); a user or organization site is still “initially configured to live under the username.github.io subdomain” (S041).
- A project site with its own custom domain configured is published at that domain's root instead of the repository-name subpath — S041’s “(unless a custom domain is specified)” (S041) and S043’s `base` of `'/'` for a custom domain (S043). S040 itself states only that a custom domain is possible. The case of a project site whose owner's user site has a custom domain is not established by S040–S043.
- [INFERENCE] A build that writes the base into its URLs (Jekyll `baseurl` through the filters, Vite `base`) fits one shape only: built for `/<REPO>/` it does not fit a domain-root publication, and built for the domain root its root-relative URLs leave a project site, so moving between the two needs a rebuild. Pages that use only document-relative references, like the round-23 snapshots of two owned project sites, are not tied to either shape by those references.

## What the lane can and cannot check offline

- Can: `scripts/base_path_audit.py` reads a local manifest `{version, basePath, pages:[{file, url}]}` and resolves each local page's reference set (`a`/`area`/`link` `href`; `img`/`script`/`iframe`/`source`/`audio`/`video`/`track`/`embed` `src`; `img`/`source` `srcset`; `video` `poster`; `form` `action`) against `basePath`, honouring the first base element with an `href`; finding reasons are `outside_base_path`, `input_invalid`, `page_outside_base_path`. Same site means same host and port after default ports are folded; http and https on one host count as one site, following S040's `http(s)` location row, so this is wider than the frozen matrix wording "other origins (scheme, host, port)", which no matrix case exercises.
- Can: the frozen 30-case matrix is `.ufo/waves/round-29/c2-matrix.json`; the counter is `python3 -B .ufo/waves/round-29/c2_matrix_count.py --root . --revision <commit>`.
- Cannot: the audit reads local files only. It cannot show what a server returns, confirm the base path a deployed site is served under, verify a custom-domain mapping, tell whether an out-of-base reference is missing or merely redirected, or identify which repository publishes a site. A clean audit says only that the audited files match the declared base path.
- Not established here: the base path, domain or build mode of any owned property; that needs an authorized read of the published property or of the Pages configuration.

## Reading a finding

- An `outside_base_path` finding means the reference leaves this project's base path, not that it is broken. On a shared owner host, an `<a href>` to another path such as `https://<owner>.github.io/<other-repo>/` may leave the base path on purpose; a subresource (`link`, `script`, `img`, `source`, `iframe`, `audio`, `video`, `track`, `embed`, `srcset` or `poster` values) outside it is the breakage class the remedies above address. The round-29 run over the round-23 GET snapshots of three owned project sites found 4 findings, all `<a href>` links to other paths on the owner host and no subresource (`.ufo/waves/round-29/real-input/out/summary.json`); whether those paths are published repositories is not established, and the run reads saved bytes from 2026-10-21, not the live sites. References to other hosts are outside the audit, so a clean verdict says nothing about them (the lucario page's only reference is a script on another host).
