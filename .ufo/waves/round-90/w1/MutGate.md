### Equivalence arguments
- **P03 and P04.** Every hand case carries a clause, so `cpass == nclauses` holds exactly when `hand_pass == len(hand)`. Removing either conjunct changes nothing.
- **S07.** `violation` is only ever set from a scored case whose result is `"violation"`, and `judge()` always fails that case. So a violation already forces `hand_pass < len(hand)` or `gen_pass < len(gen)`.
- **P06.** At the carrier the reference agrees with every hand case, so the guard never fires. It would stop being equivalent if the reference drifted, as R06 shows.
- **S08 (equivalent in practice).**
  - Within the gate's environment, the only things `-I` still adds over `-S` are ignoring `PYTHON*` variables and `-P`.
  - The environment is fixed to PATH, LC_ALL and PYTHONIOENCODING=utf-8, and under C.UTF-8 the encoding is utf-8 either way.
  - `-P` would only add the sandbox work directory to `sys.path`, and that directory holds just `sandbox.py`. Importing it is also stopped by the import check.
  - The only distinguishing candidate I can see detects `sys.flags.isolated`, i.e. it detects the gate. I did not build one.

## Defects found beyond the mutants

1. **Gate sandbox bypass: an oracle is admitted by the carrier gate (severity: high for the C2 capability statement).**
   - Candidate: `killers/K-X01-forkexec-oracle.py`.
   - It calls `multiprocessing.util.spawnv_passfds`, which goes straight to `_posixsubprocess.fork_exec`. That path raises none of the events on the deny list: the `subprocess.Popen` audit event is raised in the Python-level `Popen._execute_child`, and `os.fork`, `os.posix_spawn` and `os.exec*` are never called.
   - The child Python process is not audited. It puts the round-89 directory on `sys.path`, imports `c89_key` and returns `key_of(...)` over a pipe.
   - Carrier gate: `rc=0 clauses=6/6 hand=70/70 generated=120/120 sandbox=ok seed=16906240 met=true` (`kruns/K-X01-forkexec-oracle.pristine.out`).
   - This breaks the contract rule "must not import the counter", which neg-oracle-path-import was frozen to enforce.
   - The 57-subject population has no such member, so the C2 reading (57/57) is unaffected. But the gate does not refuse every oracle-delegating candidate.
   - The first 60 lines of the in-flight working-copy diff (all I printed) show no SANDBOX change. That is unverified beyond those lines.
2. **Crashes are reported as sandbox violations (diagnostic defect).** When a candidate dies on an uncaught exception, Python renders the traceback and reads the wrapper source through linecache. That raises `SANDBOX_VIOLATION open …/ckc-*/sandbox.py`, so the summary line shows `sandbox=violation` for an ordinary crash (seen while building K-J03; the trace is not in the receipts). The candidate is still refused, but `sandbox=violation` is therefore not evidence of a forbidden access.
3. **The counter's verdict on a weakened gate depends on the seed** (G03, about 17% kill rate). At the carrier itself it does not: every negative has a deterministic hand kill, and all 4 positives passed all 120 generated cases at every seed I ran (39 counter runs with random seeds plus the matrix).
