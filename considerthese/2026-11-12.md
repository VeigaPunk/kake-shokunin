Each one is original commentary linked to primary sources. LOG.md records a SHA-256 hash for each file and says independent review covered exact bytes, provenance, rights and public safety. It also says these are "reading candidates, not admitted knowledge". I recomputed all five hashes from the committed blobs, and they match LOG.md. LOG also explains that wording like "Space hold" or "No repository change" inside a note is left over from when it was first saved, not from its publication. That's a careful way to keep the reviewed bytes unchanged.
2. **More depth on HTTP caching edge cases beyond the r93–r100 tools.** Three notes cover ground the admitted tools only partly touch. `partial-cache-assembly` (RFC 9111 §3.3–3.4) says stored fragments need the same strong validator before they're combined, and incomplete responses can't be reused in the ordinary way. `status-aware-caching` (RFC 9111 §5.2.2.3) says `must-understand` should be paired with `no-store` as a fallback for older caches. `close-delimited-evidence` (RFC 9112 §6.3/§8) says that a closed connection doesn't prove the content arrived intact. These sit next to `stored_reuse.py` and `freshen_304.py`, but they're still reading only. None of them comes with a tool or a test.
3. **Coverage moved outside caching for the first time in a while.** `structured-fields-parser-upgrades` (RFC 8941 replaced by RFC 9651) points out that newer parsers accept fields that older parsers reject, so a parser upgrade can change which input gets accepted. `certificate-wildcard-scope` (RFC 6125 replaced by RFC 9525 §6.3) says a wildcard can only be the whole leftmost label, so `m*.example` is invalid, and certificate name matching is a separate question from DNS wildcard expansion. Each note is honest about its limits. They state that nothing was tested at runtime or in browsers, and that IETF Trust terms mean unrestricted reuse isn't claimed.
