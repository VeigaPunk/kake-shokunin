# An inherited DNS alias is a publishing dependency, not proof of a published site

Scope: defensive reasoning from supplied or operator-authorized evidence about web properties and publishing. No live property, account, DNS response, deployment, exploit, or mitigation was inspected or tested for this lesson. Example names below are hypothetical. This is not a finding about any particular property.

## A publishing dependency can be inherited

A software default may direct an unused name to an external publishing platform. That makes DNS, platform ownership, and an intentional deployment separate questions. A DNS alias is not itself proof that a site was claimed, published or exploited.

## The reported case and what it establishes

ProjectDiscovery's [security advisory GHSA-m36x-mgfh-8g78](https://github.com/projectdiscovery/interactsh/security/advisories/GHSA-m36x-mgfh-8g78) identifies Interactsh server versions before 1.0.0 as affected. Its account says a researcher initially reported a subdomain takeover for one ProjectDiscovery domain running Interactsh; an internal investigation then identified the default configuration issue across self-hosted server instances. Specifically, the pre-1.0.0 default created an `app` CNAME to `projectdiscovery.github.io` for a proposed GitHub Pages web client, including when the operator had not configured that web client. The risk described is that someone could host arbitrary client-side code at a vulnerable subdomain for a visitor. The advisory does not establish that attacker content was actually served, how many instances were exploited, or the current state of any deployment. It is evidence of a reported issue and vendor investigation, not evidence that every instance was successfully taken over. A DNS alias alone does not prove that its hostname was claimed or exploited. The current GitHub verification guidance below is a present-day defensive reference; it does not establish the verification status or exact platform behavior at the time of the original incident. [Advisory](https://github.com/projectdiscovery/interactsh/security/advisories/GHSA-m36x-mgfh-8g78); [issue #136](https://github.com/projectdiscovery/interactsh/issues/136).

The [v1.0.0 release](https://github.com/projectdiscovery/interactsh/releases/tag/v1.0.0) lists removal of the app CNAME; the advisory names 1.0.0 as patched and recommends updating. The linked merged [PR #155](https://github.com/projectdiscovery/interactsh/pull/155) specifies the operational scope: it disables the app CNAME by default and introduces an opt-in `-app-cname` flag, rather than eliminating the behavior altogether. Updating addresses that versioned default, but does not by itself prove that the flag is disabled, every externally managed or separately retained DNS record disappeared, all deployed servers were replaced, or caches and actual authoritative answers are now clean. Conversely, a separate stale CNAME need not have been generated by Interactsh. Verify the actual source and current state rather than infer them from a package label.

## Defensive decision model

1. **Bind ownership and intent.** For a name the operator is authorized to assess, record the name, its business owner, whether a Pages site is intended, and the intended GitHub user or organization and repository. A DNS CNAME is an alias returned by DNS; a repository `CNAME` file is a separate publishing-configuration artifact. An inventory entry, a repository `CNAME` file, or a successful build is not by itself evidence of DNS authority, a live deployment, or platform ownership.
2. **Separate layers and time.** Inspect the relevant version/configuration and deployed instance; the operator-controlled authoritative DNS answers and any external DNS provider records; the GitHub Pages custom-domain binding and owner; and observed serving state, each with time and source. A screenshot of one layer is not a substitute for the others. Changes and caches can make observations disagree. Minimize retained data and redact tokens, challenge values, cookies, credentials and unrelated private content.
3. **Reason from the appropriate boundary.** GitHub documents Pages domain verification at a personal-account or organization level: only repositories owned by that same account or organization may publish to the verified domain and its immediate subdomains. A verified apex covers the immediate child, not all deeper descendants. GitHub warns against wildcard DNS even with verification because a deeper name can remain at risk. These are GitHub Pages controls, not a general DNS lock or a guarantee for other hosting services. [GitHub Pages verification documentation](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/verifying-your-custom-domain-for-github-pages).
4. **Treat verification as a state, not a TXT sighting.** For an authorized account, GitHub's documented flow adds the supplied DNS TXT record, waits for DNS, then completes Verify; keep the record to maintain verification. Evidence of a TXT record alone does not establish that GitHub accepted verification, nor that the right account owns the intended publishing repository. A domain already verified by another account or organization is not released by attempting to verify it; resolve ownership through authorized channels. Verification can release an unverified domain currently used by another account, so assess operational impact before doing it. [GitHub Docs, verification and already-taken domains](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/verifying-your-custom-domain-for-github-pages).
5. **Contain the actual dependency.** If an unused alias remains, coordinate with its owner to remove it at its authoritative source, or replace it with an operator-controlled safe destination as appropriate, while managing availability, caches and dependencies. A ticket or inventory quarantine flags risk but does not change resolution. If a site is intended, coordinate a controlled binding and appropriate verification under the right owner, avoiding an exposed gap. Upgrade affected server deployments and separately inspect any independently managed DNS. Do not assume upgrading alone cleans external DNS; do not delete working records blindly. Treat unexpected content as a possible incident, preserve only necessary sanitized evidence, and involve the owner/security team. Never claim or publish to a third-party name as a test.
6. **Close only with bounded evidence.** Recheck the actual deployed version and configuration, authoritative DNS and relevant propagation, the intended Pages account's verified state and site binding, and safe expected serving behavior as applicable. Record what each observation proves, who observed it and when; unresolved layers stay open. A 200 response or a build log is not alone proof of ownership or secure binding. No universal safety, current live state, or absence of compromise follows from the source documents.

## Twelve manual adversarial cases

Each is a hypothetical evidence-review exercise, not a live test or instruction to claim a name. The expected judgment is limited to the facts supplied.

1. **A single report becomes universal exploitation.** A briefing says the researcher reported one ProjectDiscovery domain, so every pre-1.0.0 deployment was demonstrably hijacked. **Judgment: reject.** The advisory reports the initial domain and a broader investigation of the default; it does not establish an exploit at every instance.
2. **Unused web client.** An operator's pre-1.0.0 self-hosted server configuration has the affected default; no web client was intended. A reviewer says there is no relevant risk because nothing was deployed. **Judgment: reject that inference and investigate the current DNS/platform state.** The unwanted alias can exist without a configured client, which is the reported failure; the supplied facts do not establish current exploitability or compromise.
3. **Patch is treated as DNS cleanup.** A deployment record says server 1.0.0 was installed; a separately administered DNS zone still contains the old alias. **Judgment: unresolved; coordinate handling the live record.** The fix disables the default, but a binary upgrade is not evidence that the opt-in is off or that another DNS system or cache was cleaned.
4. **Quarantine is mistaken for containment.** An owner marks an unused alias “quarantined” in an asset spreadsheet, but the same DNS answer still reaches the external service. **Judgment: the alias remains, and exposure is unresolved.** Quarantine in an inventory alone does not change authoritative resolution or establish containment; the platform binding and verification state are not supplied. Investigate those layers and, if the alias is unused, coordinate removal or safe repointing and verify, preserving dependencies.
5. **The `CNAME` file is taken as live proof.** A repository has a `CNAME` file, but the Pages publishing mode, Pages settings, authoritative DNS, and deployed site are unknown. **Judgment: insufficient evidence of binding or a secure live site.** [GitHub documents](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site) a distinction between branch publishing and a custom Actions workflow: the latter ignores an existing repository `CNAME` file. A file alone cannot prove the other layers.
6. **A verified apex meets an immediate child.** The authorized organization has actually verified `example.com`, and its own repository is intended to publish `docs.example.com`. **Judgment: GitHub's documented verification scope includes this immediate child for that organization; still check the intended binding and DNS.** Verification does not itself prove deployment or content.
7. **A verified apex meets a deeper wildcard name.** The same organization verified `example.com`; wildcard DNS can cover `b.a.example.com`. A reviewer declares every depth protected. **Judgment: reject.** GitHub explicitly warns that verifying the apex covers immediate children, while a deeper wildcard-covered name can remain at risk. Assess actual DNS and remove unsafe wildcard use where appropriate.
8. **Wrong owner.** A person's account verified `example.com`; the intended Pages repository belongs to a separate organization. **Judgment: do not assume the organization can publish under the person's verification.** GitHub's documented restriction is tied to the verifying account or organization and its own repositories; resolve ownership and verify the correct setup through authorized channels.
9. **TXT is visible, Verify is not.** A DNS snapshot shows a Pages challenge TXT record, but there is no evidence of GitHub's completed verification. **Judgment: verification status unknown.** The documented flow requires the Verify step after propagation; do not delete the record solely because of this snapshot while authorized owners check its purpose and the proper account's state, without exposing its value. The snapshot does not prove which account the record belongs to or that it is needed indefinitely.
10. **Another account already verified it.** GitHub reports the desired domain is already verified by a different account. The operator proposes repeating verification to force a release. **Judgment: do not expect that to work.** GitHub says release is unsuccessful when the domain is already verified by another user or organization; resolve legitimate ownership and access with the relevant parties. Conversely, verification of an unverified domain in use elsewhere can release it, so assess impact first.
11. **Build success equals DNS success.** CI shows a successful build and publish job, but no DNS or Pages binding evidence is supplied. **Judgment: the log can establish the recorded job succeeded, but current DNS, binding and user-facing deployment state remain unproven.** Build evidence does not establish that the domain resolves to the intended service, that the intended account holds the binding, or that users see the expected content.
12. **A response is confused with origin or compromise.** A screenshot shows unexpected content at a name formerly pointing to Pages, but gives neither timing, complete source nor ownership data. **Judgment: preserve a sanitized record and escalate as possible incident, not a confirmed takeover or cleared state.** Identify the layers and time with authorized evidence; do not attempt a third-party claim or infer attribution, mechanism, or duration from the screenshot alone.
