# A Pages deployment delay is not, by itself, a failed deployment

This incident-based reasoning aid for publishers is dated 2026-11-03. It is not a finding about any particular site. All examples are hypothetical and judged manually. No live site, account, API, deployment or system was tested or changed for this lesson, and no model-weight training was performed.

## What GitHub reported

The [GitHub incident report](https://www.githubstatus.com/incidents/8tzbpcnl75jp), opened 2026-11-03, dates the degradation to **15:24–16:52 UTC on October 19, 2026**. It describes delays to Pages deployments and Actions-generated webhooks, as well as delays in run checks, logs and status updates. For part of that time, GitHub.com’s real-time updates and search also experienced disruption. The report specifies code search. GitHub reported no data loss. The account does not establish that every Pages deployment failed, that every site became unavailable, or what any individual site served. A delayed release, a failed workflow and the availability of existing content are separate questions.

The report provides three different aggregate measures. **GitHub-hosted runners began 5.13% of jobs late**, while **0.02% of workflow runs had failures**. During the initial half-hour, the Actions jobs REST endpoint returned error responses for **8.47% of its requests**. Their denominators are jobs, workflow runs and API requests, respectively. GitHub does not specify a separate exact measurement interval or finer population breakdown for each of the first two figures. The API percentage applies neither to all APIs nor to the entire incident. Reading the first 30 minutes from the reported 15:24 start suggests 15:24–15:54 UTC, but GitHub does not separately give those endpoints. No figure provides the failure probability of a particular Pages deployment or site. [Incident report](https://www.githubstatus.com/incidents/8tzbpcnl75jp).

The updates trace recovery without proving a particular deployment completed: at 15:56 GitHub warned of possible workflow-processing, site-build and webhook delays; at 16:30 it reported recovery after mitigation while warning that delays could continue. It posted normal operation at 16:56, while the resolved report gives 16:52 as the incident end. None of those timestamps independently establishes when a particular revision reached a particular site. [Incident timeline](https://www.githubstatus.com/incidents/8tzbpcnl75jp).

## Mechanism, mitigation and open cause

GitHub's incident report attributes the wider disruption to overloaded shared network capacity after a service's cache connections failed and its servers retried. GitHub describes changes to connections and subsequent processing of delayed work. This account does not establish that a particular publisher's workflow, code or network caused a delay. [Incident report](https://www.githubstatus.com/incidents/8tzbpcnl75jp).

One safeguard had been rolling out before the incident, but only in **shadow mode**, recording rather than enforcing a limit on the service's rate of opening connections. GitHub reports that it subsequently enforced that limit and capped concurrent connection attempts. It also described work to extend limits to other Actions services, add retry backoff, limit a single service's share of network capacity and improve alerting. Those further measures were ongoing in the report, with no completion dates given. GitHub was still investigating the initial connection timeouts. Thus, the underlying trigger remains unresolved on this evidence, and neither the later controls nor the planned measures establish immunity from future incidents. [Incident report](https://www.githubstatus.com/incidents/8tzbpcnl75jp).

## Publisher-side decisions under uncertainty

1. **Record the intended change and the evidence time.** Keep the intended revision, target, workflow or deployment identifier when available, relevant timestamps and the source of each observation. An incident overlapping a delay is context, not proof it caused a particular delay.
2. **Classify rather than collapse states.** Pending or late work supports “not yet confirmed complete”; an explicit failure supports “the recorded run failed”; a recorded success supports that run's reported outcome. These states do not alone tell which revision visitors currently receive. A missing or late webhook or delayed status/log is not itself proof that the underlying work failed or succeeded. Avoid declaring success or failure from an absent notification. A webhook delivery recorded as failed is a different state: GitHub documents that failed deliveries are not automatically redelivered, although manual or scripted redelivery can be arranged. The incident report says delayed Actions work was processed; it does not establish that a particular webhook was delivered or redelivered. [Failed-delivery guidance](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries).
3. **Choose a proportionate response.** During a relevant reported degradation, preserve the evidence and allow for delayed processing, taking account of the release's urgency and the operator's own procedures. Avoid assuming immediate re-runs are necessary or harmless: duplicate attempts can create confusion, and the incident report does not prescribe a universal wait time or publisher retry policy. An explicit failure or a deadline may need a different, owner-authorized response. Do not modify DNS, rebuild, republish or roll back solely because an aggregate status page reports an incident.
4. **Close the right question with the right evidence.** Once independently available, distinguish the deployment record's target revision and result from time-stamped evidence of what the intended URL served. GitHub documents that repository deployment history can show associated commits, statuses and linked workflow logs, among other details; access and the available record must be established for the particular deployment. [Deployment history](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/view-deployment-history). A successful recorded job, a resolved status page, or a response without revision-identifying content alone cannot establish that the intended revision is currently served everywhere. Resolve inconsistencies with the owner; do not infer that an earlier successful response guarantees current or global state. These are evidence-handling recommendations, not claims that GitHub guarantees any particular delay, retry, serving or propagation behavior.

## Twelve hypothetical evidence cases

These are manual tabletop judgments, not executed tests. Each conclusion is bounded by its stated evidence.

1. **Overlapping pending deployment.** A Pages deployment record remains pending during 15:40 UTC on October 19, with no failure result. **Judgment:** completion is unconfirmed; the incident is plausible context, not proof of causation or failure. Preserve the identifier and timing; assess urgency before taking an authorized next step.
2. **Explicitly failed workflow.** A workflow run tied to a deployment is recorded as failed in the incident window. **Judgment:** the recorded run failed; the aggregate report does not prove why, whether a subsequent attempt succeeded, or what users saw. Inspect the available failure evidence before deciding an authorized remedy.
3. **No webhook.** A deployment owner has no expected Actions-generated webhook, while the status and deployment outcome are unavailable. **Judgment:** the outcome is unknown. The incident reported delays in that webhook class; missing delivery cannot be equated with failure or success, and the report does not establish permanent loss for this event. If a delivery record instead shows failure, GitHub documents no automatic redelivery; identify the cause and coordinate any appropriate authorized redelivery, without assuming the deployment itself failed. [Failed-delivery guidance](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries).
4. **Job delayed, workflow failed.** Someone combines 5.13% and 0.02% to assert that 5.15% of Pages deployments failed. **Judgment:** reject. The source describes different events and denominators, and neither percentage is a Pages-deployment failure rate; adding them does not produce one.
5. **REST API rate generalized.** A slide says 8.47% of all GitHub API calls failed throughout the 88-minute incident. **Judgment:** reject. The statistic is confined to errors from the Actions jobs REST endpoint during the initial half-hour. It does not describe all APIs or the entire incident window.
6. **Delayed log interpreted as failure.** A job's logs do not update for several minutes, but no terminal result is available. **Judgment:** outcome unknown; GitHub reported delayed logs, and silence alone is not a terminal status. The cause of this particular silence remains unproven.
7. **Successful run, unknown content.** A record shows a deployment job completed successfully for the intended revision, but no evidence describes the content currently served at the target URL. **Judgment:** the record supports that job's recorded success, not current user-facing content, reachability or global consistency.
8. **Prior revision observed.** A time-stamped 200 response from a hypothetical target identifies the prior revision, rather than the intended new revision. **Judgment:** that observation supports a response serving the prior revision at that time and vantage, not publication of the intended revision or service everywhere. It does not by itself establish why the new revision was absent.
9. **Recovery message treated as per-site clearance.** GitHub's 16:30 recovery update is taken to mean a particular queue is empty. **Judgment:** reject. The update explicitly allowed continuing delays; even the later normal-status report does not by itself verify that particular deployment or served revision.
10. **A later, unrelated delay.** A different deployment is delayed the following day, with no incident-specific evidence connecting it to October 19. **Judgment:** do not attribute it to the earlier incident merely by similarity. Use the later deployment's own time-stamped evidence and any applicable current service information.
11. **Shadow mode claimed as prevention.** A review says the connection-opening limit blocked the initial surge. **Judgment:** reject. GitHub says the limit was logging only at the time, then enforced later; the report does not establish the initial timeout's cause. Separately, the other listed enhancements were described as ongoing, not completed.
12. **Deadline and duplicate attempts.** A release is still pending near a critical deadline, and an operator proposes launching several retries immediately. **Judgment:** the incident does not prescribe a universal retry decision. Weigh the deadline against duplicate-attempt and state-ambiguity risks, consult the responsible owner's procedures, and record each authorized decision and resulting run; neither waiting nor retrying guarantees resolution.
