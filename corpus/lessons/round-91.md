Admits:

- **S469 admit, A, RFC 9111 §5.2.1 line 1113–1114**: "This section defines cache request
  directives.  They are advisory; caches MAY implement them, but are not required to."
  (17 words). Grounds the contract's stance that request directives are client
  preferences the instrument evaluates, never cache obligations.
- **§5.2.1.2 line 1137–1138**: "The max-stale request directive indicates that the client
  will accept a response that has exceeded its freshness lifetime." (20 words). Grounds
  `serve-stale` and its `max-stale=N` bound.
- **§4.2.4 line 790–791**: "A cache MUST NOT generate a stale response if it is prohibited
  by an explicit in-protocol directive" (18 words). Grounds `must-revalidate-fail` and
  the `proxy-revalidate` shared-cache branch.
- **§4.2.1 line 658**: "If the cache is shared and the s-maxage response directive
  (Section 5.2.2.10) is present, use its value" (17 words). Grounds the freshness-lifetime
  order s-maxage → max-age → `Expires − Date`.

Rejects:

- **Reject (row candidate): a second row for RFC 9111 §4.2.3 age arithmetic.** S462
  already carries §4.2.3 for `cache-current-age.md`, and the new contract delegates the
  arithmetic to that reading rather than re-deriving it; a second row would be a
  within-scope duplicate of the same URL. Flip: a contract revision that re-specifies the
  age equation differently from S462's six-equation set.
- **Reject (proposition): "the contract's `Date`/`Expires` integer convention is RFC 9111's
  own form".** §4.2.1 says "its value minus the value of the Date response header field
  (using the time the message was received if it is not present, as per Section 6.6.1 of
  [HTTP])" — the RFC requires an HTTP-date and allows a missing `Date`, while the contract
  requires an integer and refuses a missing `Date`. That is a declared adapter convention,
  not a reading of the RFC; the knowledge entry must say so.
